# 课题三仿真系统详细开发设计

本文依据[开发目标与架构](课题三仿真系统重构开发文档.md)，规定拟建文件、类、主要函数及调用关系。当前仅为开发设计，文中的目录和接口尚未实现。

## 1. 实现范围

全部代码统一放在`codes/`，采用Python组织仿真及算法模块，演示页面使用HTML、CSS和JavaScript。初期单进程运行，各平面通过函数调用和内存消息交互，记录使用JSON Lines，原始证据保留为独立文件。

五个平面分别对应`base`、`attack`、`recognition`、`defense`和`presentation`。启动、场景配置、运行调度、记录和独立评估是共用支撑，不另设平面。AI用于开发时核查设备与接口依据，不作为仿真运行必需组件。

本阶段细化软件结构和调用契约。识别算法、攻击效果参数和防御策略按后续研究成果接入，不因接口或演示完成就认定达到课题指标。

运行产生的记录放在独立的`runs/<run_id>/`目录；协同方数据包从配置指定的位置读取，不混入源码。`run_id`区分同一场景的多次运行，`scenario_id`标识场景。

## 3. 共用文件

### 3.1 `main.py`：启动入口

| 函数 | 功能 |
| --- | --- |
| `parse_args() -> options` | 读取场景路径、界面／无界面模式和输出目录。 |
| `main() -> int` | 创建`Application`，启动页面或运行指定场景；结束时保存记录并返回退出状态。 |

### 3.2 `contracts.py`：数据契约

以下类型采用简单数据对象，不包含仿真逻辑。外部字段以交付规范为准，内部对象序列化后使用JSON。

| 类型 | 主要内容与用途 |
| --- | --- |
| `ScenarioConfig` | 场景标识、设备、连接、工况、步长、随机种子、业务操作、攻防配置及外部数据配置。 |
| `DeviceSpec`、`LinkSpec` | 设备类型／参数／能力，以及连接端点／端口／类型／时延／丢包配置。 |
| `Message` | `message_id`、源／目标及端口、业务类型、关联请求、创建／计划送达时间、`payload`；承载内部设备交互。 |
| `EffectRequest` | 作用标识、目标、作用类型、参数、起止时间、顺序；仅用于攻击平面向底座提交作用。 |
| `DefenseRequest` | 动作标识、关联识别结果、目标、动作、参数及有效时段。 |
| `Capability` | 目标支持的动作、参数范围、联锁条件及允许读取的管理状态。 |
| `ActionFeedback` | 动作标识、时间、受理／执行状态、失败原因和可读反馈；不将动作完成等同于防护有效。 |
| `ObservationEvent` | 对五类外部JSON事件的类型化封装，字段沿用交付规范，不加入攻击计划或内部状态。 |
| `ObservationBatch` | 当前可用事件、接收时间、关联结果及缺失／迟到信息；保留提供方原事件。 |
| `RecognitionResult` | 沿用[角色设计的识别输出](系统角色设计.md#353-攻击识别输出)，记录判断、证据引用及置信度。 |
| `DefenseResult` | 沿用[角色设计的防御输出](系统角色设计.md#355-防御措施输出)，记录动作和观测到的前后变化。 |
| `StepResult` | 本步内部状态、消息记录、动作反馈及作用记录；只交调度、记录和独立评估，不整体传给算法。 |
| `EvaluationResult` | 沿用[评估输出](系统角色设计.md#36-评估者)，保留有效样本数、比较依据和不可评估原因。 |

内部仿真时间统一为相对场景起点的整数微秒，参数名称使用`time_us`、`dt_us`。外部事件保留原始带时区时间；配置显式声明其与仿真时间的对应关系，不能用设备受扰后的时间改写调度时钟。

观测引用通过`event_key(provider_id, event_id) -> str`统一生成，采用二元素JSON数组的字符串表示，保留原始事件ID；识别结果的`evidence_event_ids`和防御结果的`trigger_event_ids`使用该键查询证据。

`ActionFeedback`的执行状态采用`accepted/rejected/executing/completed/failed`；`DefenseResult.status`沿用原规范。`completed`只表示执行完成，只有后续观测满足策略恢复条件才记为`succeeded`；证据缺失时保留未确认说明。

### 3.3 `scenario.py`：场景装配

| 类／函数 | 功能 |
| --- | --- |
| `load_scenario(path) -> ScenarioConfig` | 读取JSON配置，解析相对数据路径。 |
| `validate_scenario(config) -> list[error]` | 检查实体标识、连接端口、单位、动作能力、时间参数及数据来源引用。 |
| `create_device(spec) -> Device` | 从`DEVICE_TYPES`映射按类型创建实例；未知类型明确报错。 |
| `register_device(type_name, factory)` | 注册新增设备的构造函数，避免在调度器中添加类型分支。 |

`substation.json`的范围如下：

| 配置项 | 内容 |
| --- | --- |
| `simulation` | 步长、时长、随机种子、场景时间起点。 |
| `devices` | 实例ID、模型类型、过程／间隔／站控归属、端口、初值、参数和可控能力。 |
| `links` | 端点与端口；区分物理耦合、电气连接、硬接线、有线消息和无线消息。 |
| `environment` | 负载、环境温度及电磁／声波／信道条件；各简化模型的参数与适用范围。 |
| `operations` | 正常业务操作的目标、动作、设定值和计划时间。 |
| `attacks` | 作用计划、时间／步序依赖、对应效果模型及参数依据。 |
| `recognition`、`defense` | 启用的检测器／策略及参数，分别传给对应平面。 |
| `observations` | 数据包路径、提供方／节点映射、时间对应、五类接口可用性及回放／交互模式。 |
| `evaluation` | 正常／无防御／有防御模式、基准运行引用、判定窗口与指标规则。 |
| `references` | 模型、设备接口及参数的资料引用；关联现有依据说明或具体资料位置。 |

相同变电站拓扑可通过配置形成三类对照运行。场景装配时按职责拆分配置；识别与防御不能获得包含攻击计划的完整`ScenarioConfig`。

### 3.4 `application.py`：运行调度

`Application`持有各模块实例，负责调用顺序和运行状态。仅该模块组装完整运行上下文。

| 方法 | 功能 |
| --- | --- |
| `load(config_path) -> run_id` | 校验场景，创建底座、接入器、攻击计划、识别器、防御器和记录目录。 |
| `start()`、`pause()`、`stop()` | 控制运行；暂停时冻结仿真推进，停止时保存结束状态。 |
| `step() -> step_summary` | 按第9节的顺序推进一次仿真，返回供展示使用的摘要。 |
| `submit_operation(request) -> receipt` | 校验UI／场景操作并排队，在下一步边界交给相应模块处理。 |
| `get_view(view_name, query) -> dict` | 提供限定用途的展示数据，不暴露可修改的底座对象。 |
| `replay(run_id, time_us) -> dict` | 读取已保存记录形成指定时刻视图，不再次执行攻击或防御。 |

运行状态为`ready/running/paused/finished/error`。初期只同时运行一个场景；UI请求进入操作队列，由同一调度循环更新状态，避免UI线程和仿真同时写设备。

### 3.5 `records.py`、`evaluation.py`：记录与评估

| 文件／类 | 主要方法 | 功能 |
| --- | --- | --- |
| `records.py`／`RunRecorder` | `append(stream, record)`、`save_manifest(config_summary)`、`close()` | 分流保存业务、观测、识别、防御、内部真值和运行元数据，保留原始证据索引。 |
| `records.py`／`RunReader` | `read(stream, time_range)`、`snapshot_at(time_us)` | 按记录时间查询事件及已存状态，供UI回放和独立评估使用。 |
| `evaluation.py`／`Evaluator` | `evaluate(run_records, rules)`、`compare(baseline, defended)` | 对照真值计算识别指标，比较有效攻击下的防护与业务恢复效果。 |

每次运行至少保存已解析配置及其摘要、模型／算法版本、随机种子和外部数据版本。完整配置随内部记录保存。内部状态快照用于展示回放；外部观测流、模型真值流分开保存，识别模块仅得到观测读取入口。

指标分母必须来自有效样本和已约定判定规则。没有有效攻击、缺少匹配对照或缺少后续观测时返回不可评估及原因，不记为100%成功。对照运行保持设备、工况和随机条件可比，并注明外部数据是否对应相同条件。

## 4. 仿真底座平面

### 4.1 `base/device.py`：设备公共接口

`Device`保存`asset_id`、端口、参数、内部状态和能力。各设备复用同一接口，由子类实现具体业务。

| 方法 | 功能 |
| --- | --- |
| `receive(message)` | 接收并校验已送达的业务消息，更新输入缓存或待执行请求。 |
| `set_effects(modifiers)` | 由底座设置当前有效的影响参数，空集合表示移除临时影响；不直接重置物理状态。 |
| `step(time_us, dt_us, inputs) -> list[Message]` | 按采样／控制周期更新本设备，生成待发送消息；`inputs`只包含已配置的物理输入。 |
| `capabilities() -> list[Capability]` | 返回设备实际支持的动作及参数范围。 |
| `request_action(request) -> ActionFeedback` | 接收底座分派的动作，检查能力和联锁，登记执行及反馈时序。 |
| `read_management() -> dict` | 返回管理接口实际可读的状态，供防御查询。 |
| `snapshot() -> dict` | 输出模型内部状态，供记录、评估及标明来源的UI视图使用。 |

设备只更新自身状态，通过消息或底座的物理模型影响其他实体。简单实例使用参数区分，只有业务行为明显不同才增加子类。

### 4.2 `base/process.py`：过程层

| 类 | 对应实体／功能 | 主要专用方法 |
| --- | --- | --- |
| `PrimaryEquipment` | 一次设备及辅助系统的公共基类，保存物理状态、设定值和可控部件。 | `physical_outputs()`：给出配置测点处的物理状态，仅供底座传导与感知模型使用。 |
| `SwitchEquipment` | 开关类；按配置区分断路器、隔离开关、接地开关能力。 | `check_interlock(action, inputs)`：检查分合条件；`step(...)`：计算动作延时、位置和连接变化。 |
| `TransformerEquipment` | 变压器及分接机构。 | `step(...)`：推进档位、变比及简化热状态。 |
| `CompensationEquipment` | 可投切无功补偿设备。 | `step(...)`：更新投切状态和无功输出。 |
| `AuxiliaryEquipment` | 风机、油泵等辅助系统。 | `step(...)`：更新启停／转速及冷却能力。 |
| `SensorDevice` | 感知设备；电流、电压、温度、压力或振动通过测点配置区分。 | `sample(physical_input, time_us)`：计算带量程、误差和时序的传感读数。 |
| `AcquisitionDevice` | 采集与处理设备；配置为合并单元或状态采集／分析装置。 | `build_measurement(time_us)`：整理通道、单位、质量和采集时间，按实例保留SV相关字段。 |
| `ControlInterfaceDevice` | 智能终端、驱动控制器及执行接口。 | `translate_command(message)`：转换为目标支持的动作；`build_feedback(time_us)`：上报可读位置／档位／运行状态。 |

专用方法由公共`step()`或`receive()`调用。传感器产生的是底座内部业务读数；它不生成协同方的电磁I/Q、声波PCM或网络IDS证据，也不自动将内部读数包装成外部业务量测事件。

### 4.3 `base/bay.py`、`base/station.py`：间隔层与站控层

| 文件／类 | 主要方法 | 功能 |
| --- | --- | --- |
| `bay.py`／`ConditionMonitor` | `summarize(measurements)` | 汇集状态采集数据，按业务规则上报设备状态与告警；不是课题三攻击识别器。 |
| `bay.py`／`ProtectionDevice` | `evaluate_protection(samples, time_us)` | 根据量测、定值和持续时间判断保护动作，生成跳闸及保护事件。 |
| `bay.py`／`MeasurementControlDevice` | `build_telemetry()`、`check_command(command)` | 上送量测，检查操作条件，向控制接口转发操作并跟踪反馈。 |
| `station.py`／`StationControlSystem` | `submit_operation(operation)`、`update_overview(message)` | 发起正常站端操作，汇集量测、状态和事件。 |
| `station.py`／`TimeService` | `time_signal(time_us)` | 按时间源状态输出设备可接收的对时信号／同步状态；独立于仿真调度时钟。 |

以上类均继承`Device`。`StationControlSystem`是被仿真的站端设备角色，`presentation`是整个研究系统的UI，两者分别承担业务控制与演示职责。

### 4.4 `base/communication.py`：连接与消息

| 类／函数 | 主要方法 | 功能 |
| --- | --- | --- |
| `WirelessTerminal(Device)` | `encode_message(message)` | 将采集数据封装为内部无线消息，保留业务来源。 |
| `WirelessGateway(Device)` | `forward_message(message)` | 按接入配置向站内网络转发已接收消息。 |
| `CommunicationNetwork` | `send(message, time_us)`、`deliver_due(time_us)` | 按配置路由消息，计算时延／丢包，维护待投递队列并交付到期消息。 |
| `CommunicationNetwork` | `link_status(link_id)`、`set_link_effect(effect)` | 查询链路状态并接收底座施加的限时链路影响。 |

网络类对应架构中的站内通信网络，同时管理可选无线传输段；终端、网关仍是独立设备实例。硬接线可复用轻量投递队列，但不计为以太网流量。物理耦合、电气连接由环境模型处理，不送入网络队列。

内部消息分为采样／状态、命令／设定、执行反馈、保护事件、对时五类，`payload`沿用[架构的实体接口表](课题三仿真系统重构开发文档.md#22-实体间的接口)。SV、GOOSE等作为实例的语义和必要字段保留，不在初期实现完整协议栈或伪造对应PCAP。

### 4.5 `base/environment.py`：工况与影响传导

| 类／函数 | 主要方法 | 功能 |
| --- | --- | --- |
| `OperatingEnvironment` | `update(time_us, dt_us, physical_outputs)` | 根据电气拓扑、设备输出和负载／环境温度，更新共享工况。 |
| `OperatingEnvironment` | `inputs_for(asset_id)` | 沿配置连接给设备提供局部物理输入，不向算法暴露全局物理真值。 |
| `EffectModel` | `evaluate(request, local_conditions) -> modifiers` | 按目标敏感性、频段／条件和作用参数计算读数偏移、时钟偏移、执行延迟或链路退化等影响。 |
| `register_effect(effect_type, model)` | — | 在`EFFECT_MODELS`映射中注册可替换的影响模型。 |

电气模型先表达开关拓扑、分接变比、负载及补偿对量测的影响；热模型先表达负载、损耗、环境温度和冷却能力的关系。模型说明必须列出输入、输出、单位、参数依据及适用范围；不将简化结果宣称为高保真电磁暂态计算。

电磁、声波等在这里是作用条件和影响参数，不是原始波形生成器。底座每步调用效果模型，将有效`modifiers`分派给设备的`set_effects()`或网络的链路影响接口。效果到期移除；已造成的设备动作、损坏或热状态按模型继续演化，不自动恢复初值。

### 4.6 `base/engine.py`：底座引擎

| `SimulationEngine`方法 | 功能 |
| --- | --- |
| `build(device_specs, link_specs, environment_config)` | 创建设备、网络及环境，完成端口和关系绑定。 |
| `submit_effect(request) -> receipt` | 校验作用目标和效果类型，按起止时间登记；未知目标或不支持的效果拒绝并记录。 |
| `submit_defense(request) -> ActionFeedback` | 检查能力、联锁和动作冲突，将动作分派给目标设备／链路。 |
| `submit_business_operation(operation) -> receipt` | 将正常业务操作送往配置的站端或就地控制入口，保留业务链路。 |
| `step(time_us, dt_us) -> StepResult` | 推进工况、设备、消息和到期动作，产生本步结果。 |
| `get_capabilities(target_ids)`、`get_management(target_ids)` | 向防御提供限定目标的能力和可读管理状态。 |

正常控制、防御控制最终进入同一目标的动作检查。同一时刻冲突按场景声明的优先级处理；不能绕过开关联锁、设备范围或超时规则。业务补偿以有期限、有来源标记的替代值作用于允许的消费端，保留原始量测和物理状态。

### 4.7 `base/observations.py`：五类外部数据接入

五类接口共用接入流程，按`source_type`校验，无需为每类重复实现一套传输服务。该文件只消费协同方交付物。

| 类／函数 | 主要方法 | 功能 |
| --- | --- | --- |
| `ObservationSource` | `read_available(time_us) -> list[dict]` | 数据源接口：返回此时已可交付的事件；不接受隐含攻击答案。 |
| `ObservationSource` | `sync_context(context) -> receipt` | 可选交互能力：传递协商允许的工况／控制反馈；固定文件源明确返回不支持，不能据此生成新证据。 |
| `FileObservationSource` | `read_available(time_us)` | 按配置的交付时间表读取JSONL和证据索引，支持固定回放。 |
| `ObservationGateway` | `ingest(records, received_at)` | 校验Schema、元数据和证据引用，按`provider_id + event_id`去重，保留退化及缺失记录。 |
| `ObservationGateway` | `window(start_us, end_us, source_types) -> ObservationBatch` | 提供已收到且属于查询窗口的观测；返回明确的缺失、迟到和关联状态。 |
| `associate_event(event, mapping, time_mapping)` | — | 按显式配置关联设备与场景时间，保留原事件、原时间及映射依据。 |
| `EvidenceReader` | `describe(event)`、`read_segment(event, start, count)` | 检查文件格式和采集配置，按需读取证据片段；不一次加载所有波形。 |

`EvidenceReader`按SigMF、WAV、EVE／PCAP、CSV分别处理；不支持的编码或协议明确返回错误／不可解析信息。原始样本不具备校准、解码或定位条件时，不补造功率、真实身份或方位。

接入错误单独记录，不能将坏文件伪装成有效数据。提供方明确上报的`missing`事件原样保留；本方等待超时只形成接入状态，不冒充提供方生成监测事件。证据引用使用提供方和事件标识共同定位，避免不同提供方事件编号碰撞。

固定文件回放只支持接入、算法离线处理和展示。需要闭环验证时，由协同方适配器实现`ObservationSource`，按双方约定接收可共享工况／控制反馈并返回匹配观测；在该能力落实前，相关运行标记为回放验证。

## 6. 识别平面

### 6.1 `recognition/engine.py`

| --- | --- |

## 9. 单步运行顺序

`Application.step()`按固定顺序调度，算法及UI均不另行推进仿真时间：

1. 在当前步边界接收排队操作，提交到期攻击步骤及上一轮防御请求，激活或移除到期影响。
2. 底座按上一时刻已提交状态更新共享工况，投递已到期消息，各设备按自身周期执行一次状态更新。
3. 提交设备新状态和待发送消息，计算消息送达时刻，汇总动作反馈；新消息最早在下一步投递，避免零时延递归。
4. 接入当前已交付的外部观测，校验和关联后更新识别窗口；需要协同方交互的数据源在约定时点同步工况／反馈。
5. 识别平面给出判断，防御平面结合观测和可读能力生成下一步处置，并检查既有动作的恢复情况。
6. 分流保存本步结果，更新UI摘要，推进调度时钟。

设备采样周期可为底座步长的整数倍。消息实际投递取不早于计划时间的首个步边界，记录计划与实际时间；时间分辨率不足时缩小步长，不宣称能验证短于步长的效果。

观测只在实际交付后可见，不因文件含有未来样本而提前提供给识别。无法映射时间的事件保留但不强行纳入跨域时序判断；迟到事件可更新离线分析，不反向改写已经执行的在线防御。
